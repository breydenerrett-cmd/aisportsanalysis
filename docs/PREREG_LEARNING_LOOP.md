# PREREG: the Hounds learning loop (champion / challenger)

Registered 2026-10-18, BEFORE any code of the learning loop exists
(`src/hounds/learning/`) and before any challenger has been proposed, run or
measured. Nothing below was tuned to a number; the numbers are chosen from the
statistics of the design (what a 100-slot sample can and cannot detect) and
from the failure this loop exists to prevent. A change to any number or rule is
a NEW dated section in this file first, never a quiet edit of the old one.

PAPER ONLY. Every hound makes simulated flat one-unit bets. No part of this
loop places, sizes, routes or suggests a real bet, and nothing here claims an
edge or a profit. The -200-or-worse cap (owner rulings 2026-09-20 and
2026-09-22) is enforced in code on every bet a challenger shadows, exactly as
it is for the champion; it is not a setting and no proposal can touch it.

## 0. Why this exists, and the failure it must not repeat

The owner wants a system that keeps learning across every strategy and bet
type. The reference project (beebots) put an AI coach in front of its bots'
rules: it rewrote them 29 times in 11 days and rolled back none. A later
review called that statistical malpractice, and it was right: a rule rewritten
toward last week's results chases noise, and a system that never undoes a
change cannot tell whether it is improving. Our own loss diagnosis
(`docs/research/loss_diagnosis/00_SYNTHESIS.md`) found the same failure in the
public card.

So the loop has two jobs, in this order:

1. **Change a champion only when the evidence says so**, by a rule written
   here, decided by code, never by a model.
2. **Be able to prove whether it is improving at all** (section 9), and stop
   itself when it cannot (section 10).

## 1. Who may do what

| Actor | May | May never |
|---|---|---|
| The coach (a frontier model, via the signed door or the CLI) | PROPOSE a challenger: a spec, a written hypothesis, and the evidence it read | promote, retire, edit a champion, write a ledger row other than a proposal |
| The shadow runner (code) | run every live challenger on the same games at the same prices as its champion, forward only | bet a game whose lock has passed; bet at -200 or worse; touch a champion's rows |
| The referee (code, sections 5 to 7) | measure, decide, promote, retire | take instruction from any text in a proposal |
| The owner | switch the coach on or off, resume after an auto-pause, undo a coached version, retire any hound | (nothing is off limits; these are the only gates the loop needs) |

A model's text (hypothesis, reason, quip) is quoted, never executed or
interpreted, and goes through the same language filter as a hound's name.

## 2. What a challenger is

A **champion** is the one version of a hound that races publicly. A
**challenger** is a proposed new version, run in shadow beside its champion.
A champion is never overwritten: a promotion creates a NEW version, and the old
version keeps its own record, visible, for ever (section 8).

### 2a. User hounds

The challenger spec is a spec of the fixed menu (`src/hounds/user_spec.py`),
validated like any form post. Frozen across the pair, so that the pair sees the
same boards at the same instants: `name`, `tagline`, `lock_minutes`. Allowed to
change but only to NARROW (the existing coach guards): `sports` and `markets`
may only stay or shrink; `max_bets_per_day` may only stay or go down;
`min_books` may only stay or go up; the price band may only stay or narrow.
`side_rule` may change within the markets still held. A spec with the same rule
hash as the champion is not a challenger.

### 2b. House pack hounds

A pack hound is tunable only through knobs declared in `config/house_pack.json`
under `tunable`: for each knob the module attribute that holds it, its default
(which MUST equal the live value; a test holds the config and the code
together), its `min`, `max` and `step`, and the exact strings of the hound's
`rule_text` that state it (`renders`). A challenger is a set of knob values: at
most 2 knobs different from the champion's, every value inside `[min, max]`
and on the `step` grid from `min`. Its published rule text is GENERATED by
substituting the renders into the champion's text, so the words always say what
the code does. A hound with no `tunable` entry cannot have a challenger. The
declared knobs are conservative (a window around the default, never an
unbounded range).

Not covered, by design: engine-backed hounds (the signal systems, the
baselines), the two seeded random controls and the two esoteric entertainment
hounds (controls and fun do not get tuned), the hounds whose price band is a
class constant, the AI desk and the Old Dog. The analyst brief prompt has its
own challenger arm (section 12).

## 3. Proposal guards (all enforced in code, in this order)

1. The kill switch is on (`config/hounds_coach.json` `enabled: true`) and the
   loop is not auto-paused (section 10). Default OFF.
2. User hounds: the signed round (one-use key, 15 minutes, HMAC over
   `ts.POST.path.body`; a wrong signature does not burn the key) and the
   owner's opt-in. Pack hounds: the operator CLI (`python -m src.hounds.learning
   propose`), because the ledger lives in the repository, not on the API
   volume; the same guards apply except the signature.
3. The hound's current champion version has at least 50 graded forward bets.
4. At most ONE accepted proposal per hound lineage per 7 days (a held round
   uses the allowance too).
5. At most 3 live challengers per hound and 30 live system-wide.
6. The proposal carries a hypothesis (20 to 400 characters: why this should
   beat the champion) and the evidence it read (1 to 10 references to
   scorecard fields or lesson ids).
7. The spec obeys section 2.
8. **No repeats.** A proposal is refused if it is a near-duplicate of (a) its
   champion, (b) a live challenger of the same hound, or (c) a challenger of the
   same hound RETIRED (lost or never won) in the last 90 days. Near-duplicate
   means: user hounds, `sports`, `markets`, `side_rule` equal and
   `price_min`, `price_max` within 0.10 decimal odds, `min_books` and
   `max_bets_per_day` within 1; pack hounds, every knob within one `step` of
   the other's. A challenger retired as superseded or expired does not block a
   repeat: it never lost.
9. Every refusal is recorded in the learning ledger (code and message), so the
   monthly review can see what the coach tried.

## 4. Shadow running

* Forward only. A challenger bets a game only if its lock is at or after the
  instant its proposal was accepted. No replay, no backfill, ever.
* The same engine, the same games, the same board at lock, the same price
  conventions as its champion: user challengers run `user_engine.run`, pack
  challengers `pack_run.run`, on the same rows and the same clock. A test pins
  that a challenger identical to its champion produces rows identical in every
  price, line and lock field.
* Its rows go in a challenger ledger (hash-chained, separate from every
  champion ledger and from every public source) tagged `role: "challenger"`,
  `challenger_id` and the parent champion id and version. They never appear on
  the race, the stream or the graveyard.
* The same daily cap and the same -200 cap as the champion.

## 5. The comparison: the only thing that can promote

The unit is the **paired slot**: one game and one market (`event_id`,
`market`). For a slot where the champion or the challenger or both bet, each
side's value is its bet's closing-line value in points
(`clv_pts`, section 1 of `docs/PREREG_HOUND_VERDICT.md`, unchanged), and the
paired difference is

    d = clv(challenger) - clv(champion)

with these rules, frozen:

* A bet counts only if it is **measurable** (the referee's rule: forward, locked
  before the start, fresh close). A slot where a side that bet is not
  measurable is EXCLUDED (not counted as zero); the exclusion count is shown.
* **A pass counts as 0** (the side that did not bet in that slot has value 0).
  A slot where both pass is not a slot.
* The champion's bets for the pair are those of the champion version the
  challenger was born under, from the challenger's start onward.
* **Volume floor, against winning by abstaining.** Because the price taken
  carries the book's margin, a typical bet's CLV is below zero, so "pass" beats
  a mediocre bet by construction. A challenger that simply bets less would win
  for the wrong reason. So a look can promote only if the challenger has at
  least 50 measurable bets AND at least 50% as many measurable bets as the
  champion over the same slots. Below that the look is recorded and cannot
  promote.

## 6. The sequential test

Looks happen at **100, 150, 200, 250 and 300 paired slots**. Look k uses the
FIRST n_k paired slots in order of lock time (ties: event id, market), so the
result does not depend on when the referee happened to run. The maximum
sample is 300 paired slots. A look needs at least 20 distinct slate dates in
its sample; below that it waits for the next look's size.

Statistic. Slates are clustered (a market-wide move on one day moves every
game). With slots grouped by slate date d (D groups, s_d the sum of differences,
n_d the count, N the total), the mean is `m = S / N`, the cluster-robust
variance is

    var(m) = (D / (D - 1)) * sum_d (s_d - m * n_d)^2 / N^2

and `t = m / sqrt(var(m))`, referred to Student's t with D - 1 degrees of
freedom. `p` is the one-sided p-value for "challenger better".

Spending (one-sided, total 0.025 per challenger, split over the five looks,
more at the end where the sample is largest):

| look | 1 (100) | 2 (150) | 3 (200) | 4 (250) | 5 (300) |
|---|---|---|---|---|---|
| alpha_k | 0.002 | 0.003 | 0.005 | 0.007 | 0.008 |

By the union bound the chance a challenger with a true difference of zero ever
crosses is at most 0.025 whatever the correlation between looks.

* **Promotion boundary (stage 1):** `p <= alpha_k` AND `m > 0` AND the volume
  floor holds. This makes the challenger ELIGIBLE. It is not promotion; see 7.
  Equivalently: the lower (1 - alpha_k) bound of the paired mean difference is
  above 0.
* **Harm boundary:** the one-sided p-value for "challenger WORSE" is at most
  `alpha_k` (equivalently, the upper (1 - alpha_k) bound of the paired mean
  difference is below 0). The challenger is RETIRED at once. (Retiring is the
  safe action; it takes no further control.)
* **No win at the maximum:** a challenger that reaches 300 paired slots and has
  not been promoted is RETIRED ("no win at 300").
* **Expiry:** a challenger with fewer than 100 paired slots 180 days after its
  start is closed as UNDECIDED ("expired"); the same for a challenger whose
  champion changed during its test ("superseded"). Neither counts as a loss.

What this can and cannot detect (computed before any data, for the owner):
with a paired difference standard deviation of about 3 points per slot, look 1
(100 slots) cannot be crossed by a true improvement smaller than about 1.0
point; the final look (300 slots) by about 0.5 point. Smaller real improvements
will be missed, on purpose: the loop prefers to change nothing.

## 7. System-wide false-discovery control (stage 2)

Many challengers are tested at once; a 0.025 error rate on each is not 0.025
across all of them. So promotion is decided in **batches by calendar month
(UTC)**, after the month has ended:

1. **The family** for month M: every challenger that had a look dated in M
   (look date = the slate date of the paired slot that reached the look size)
   and was still live. Its **representative look** is the first look in M that
   crossed stage 1, else its last look in M.
2. Each family member's adjusted p-value is `p_adj = min(1, 5 * p)` of its
   representative look (Bonferroni over the five planned looks, which makes it
   a valid p-value for the sequential procedure).
3. **Benjamini-Hochberg at q = 0.10** over the family of size m: sort the
   adjusted p-values ascending, p_(1) <= ... <= p_(m); find the largest i with
   `p_(i) <= i * q / m`; reject (candidates to promote) the i smallest. A
   rejected challenger must also be stage-1 eligible; one that is not stays
   live.
4. Caps on the rejected set, applied in ascending `p_adj` order: at most ONE
   promotion per hound per 30 days; at most 3 promotions system-wide per
   calendar month. A challenger rejected by BH but blocked by a cap stays live
   and is reconsidered next batch (it is not retired).
5. A stage-1-eligible challenger that fails BH stays live, except at look 5,
   where it is retired ("no win at 300: did not survive the false-discovery
   control").
6. When a hound's champion changes, its other live challengers are closed as
   UNDECIDED (superseded): their pairing partner no longer exists. The coach
   may re-propose against the new champion.

BH assumes independence or positive dependence; challengers of one hound share
a champion and so are positively dependent, which is the favourable case. The
per-challenger spending of section 6 stays in force as a second, independent
guard.

**False-discovery budget** shown on the scorecard: `q = 0.10`; promotions this
month against the cap of 3; and the **expected-false-promotions bound**, the sum
of the adjusted p-values of every promoted challenger (each is an upper bound
on that promotion's chance of being a null result).

## 8. Promotion, retirement, lineage

* **Promotion.** The challenger becomes the next VERSION of the hound.
  User hounds: `user_store.create_version` (the old version is retired as
  "superseded", its ledger and record untouched; the new version has a new id
  and a fresh record). Pack hounds: a `promotion` event makes the challenger's
  knob values the champion's from the next lock; every later bet row carries
  `hound_version` and the knobs. The public race shows the CURRENT version; the
  earlier versions appear with their own records (retired, "superseded by
  version n+1"), never merged.
* **Retirement.** The challenger goes to the "tried and failed" list with its
  hypothesis, spec, paired statistics and a one-line lesson (section 9).
* **Lineage** for a hound: every version with its record, the live
  challengers, the tried-and-failed list and the lessons.
* No row of any ledger is ever rewritten or deleted.

## 9. Lessons memory, and "is it improving?"

### 9a. Lessons

`evidence/hounds_lessons_v1.jsonl` (hash-chained, append-only; the user-hound
scope writes the same shape beside the app database). One row for every
challenger that reaches an end state: its hypothesis (quoted, as the coach
wrote it), the spec difference from the champion, the outcome (`promoted`,
`retired`, `undecided`), the paired statistics (n, dates, mean difference,
bounds, p, adjusted p, look), and a one-line **lesson generated by code** from
those numbers (no model writes a lesson). The coach's scorecard payload carries
the hound's last 10 lessons and the system-wide lessons for its category, so
the same failed idea is not proposed twice; section 3.8 refuses it if it is.

### 9b. The system scorecard (daily)

Computed once a day by the CLI, stored as an event, served at
`GET /hounds/learning`:

* **(a) Promotion hit rate.** Of promoted challengers whose new champion
  version has at least 100 measurable bets since promotion ("matured"), the
  share whose mean closing-line value over those next 100 measurable bets is at
  or above the replaced champion's mean over the paired slots of the test that
  promoted the challenger. Null until a promotion has matured. (Selection makes
  some regression to the mean expected; the floor in section 10 allows for it.)
* **(b) Are we better than chance.** The champions' mean forward CLV over the
  last 30 and 90 days against the two random control hounds (Coin-Flip Collie,
  Dartboard Dalmatian) on THE SAME GAMES: both means are taken only over the
  games on which at least one champion and at least one control had a
  measurable bet, with the pooled per-bet means and their counts shown. Null
  below 50 measurable bets on either side. Champions are every running hound
  that is neither a baseline nor a random or esoteric control or entertainment
  hound. This is the only honest "are we better than chance" line; the price
  taken carries the margin for both sides, so the difference is the point.
* **(c) Activity and budget.** Proposals, refusals, promotions, retirements,
  undos (coach changes the owner reversed), live challengers against the caps,
  and the false-discovery budget of section 7.

## 10. Auto-pause

Evaluated by the daily scorecard. The loop PAUSES (the coach kill switch flips
itself off, the dashboard says why, only the owner can turn it back on with
`python -m src.hounds.learning resume`) when EITHER:

1. at least **10 promotions have matured** and the promotion hit rate is below
   **0.40**; or
2. the champions' rolling-30-day mean CLV (section 9b) is below the random
   controls' on each of the **last 60 daily scorecards** (every one of the 60
   calendar days has a scorecard and every one shows the difference below zero;
   a missing day or a null comparison counts as not trailing, so a missed run
   can never cause a pause).

While paused: no proposal is accepted and no challenger is promoted (looks,
harm retirements and expiries still run, and the lessons still get written).
The floors are deliberately blunt. 0.40 with n = 10 is a brake on a loop that
is plainly not helping, not a test of it: a loop doing nothing would sit at
0.5 and trip it about one time in six.

## 11. The monthly director review

`python -m src.hounds.learning director-pack --month YYYY-MM` writes ONE
request file for a frontier model to review the whole system: every hound's
record, the lessons, the system scorecard, the month's proposals and refusals,
the live challengers and the open defects the tests report. Its answer is
advice saved to `docs/director/YYYY-MM.md` by a person; nothing reads that file
back into the loop and nothing in it is applied automatically.

## 12. The analyst prompt arm

The AI analyst brief prompt (`src/analyst`, `PROMPT_VERSION`) gets the same
structure: a challenger prompt is run in SHADOW on the champion's own FROZEN
packets (same packet, same game, answers saved to a challenger store, never
published, never shown), and is promoted only by the same machinery on graded
calls. The unit is the game; the value of a game is the paper units of its
TAKE calls at their published prices (a PASS is 0), paired by game. The values
are win/loss units, which are far noisier than closing-line value, so the
samples are larger and the rest of sections 5 to 7 is unchanged: looks at
**150, 225, 300, 375 and 450 paired games** (maximum 450), the same spending
table, the same BH family (analyst challengers join the system-wide family),
the same caps. Exactly one analyst prompt challenger may be live at a time.
Promotion changes which prompt text the next run uses, as a new prompt version;
the old version's published rows are never touched. The volume floor of
section 5 does not apply (a game's calls are not "bets" in the same sense);
instead a challenger must have TAKE calls in at least 50% as many games as the
champion. **No model call is made by anything in this loop's tests or by the
scorecard, referee or director commands.**

## 13. Not claimed

This loop does not claim that any champion has an edge, that a promotion
improves anything (section 9 exists to find out), or that closing-line value
is profit. A system that promotes nothing for months is working as designed.
