## Gap table (ranked by decision value for a first-customer launch)

| Rank | Missing signal | Why it matters for launch decisions | Effort to add |
|---|---|---|---|
| 1 | Signup started vs. signup submitted conflation | Right now nobody can compute "signup page view -> submit" conversion at all — the single `signup_started` kind mixes page-loads with completed account creations, so `admin/funnel`'s own `landing_view -> signup_started` conversion percentage is not measuring what it claims to. This is the single most decision-relevant number for a launch funnel and it is currently wrong, not just missing. | Small — split into a distinct client-side `SIGNUP_FORM_VIEWED` (public, anonymous) and keep the existing server-side `SIGNUP_STARTED` for the actual row-creation, or rename one of the two kinds. |
| 2 | CTA click | Without it, there's no way to tell whether a weak landing_view->signup ratio is a copy problem (nobody clicks) or a form problem (they click but bail on the form) — the single highest-leverage landing-page optimization signal is invisible. | Small — one client-side event on each CTA anchor's click, before navigation. |
| 3 | Free Bet Check used / feature doesn't exist | The landing page actively promises "3 Bet Checks free, no card required," but the backend requires auth+paid access for every bet-check call. This isn't just missing instrumentation — it's a live product/marketing mismatch that will confuse or block the first real visitors who try the advertised flow. | Not an instrumentation fix — needs a product decision (build the anonymous free-tier path, or change the landing copy) before an event can even be designed. |
| 4 | Cancellation in the funnel view | `subscription_cancelled` is recorded and visible in the 14-day overview rollup, but invisible in `GET /admin/funnel`'s step list, so there's no single view showing the full acquisition-through-churn picture during the beta. | Trivial — append `events.SUBSCRIPTION_CANCELLED` to `FUNNEL_STEPS` (as a step off the activation branch, not chained to raw signup counts, since it's a rate off active subscribers, not off `bet_saved`). |
| 5 | Return visit / retention | For a subscription product, whether a paying customer comes back is arguably as important as activation itself, and currently there's no way to answer it without a manual DB query. | Medium — needs either a stored "first_seen_day"/"last_seen_day" per user_hash, or a small aggregation function alongside `daily_counts_by_kind` that counts distinct-day-count per user for page_view/bet_check_run/digest_viewed. |
| 6 | First Today/Gameday view breakdown | `page_view` events already carry a `route` property, but no admin surface breaks it out — right now "did people go straight to Today, or browse Games first?" is unanswerable without a raw SQL/`list_events()` scan. | Small — extend `daily_counts_by_kind` (or a sibling function) to group by `(kind, properties.route)` for `page_view` specifically. |
| 7 | Activation event naming | Functionally wired (see step 8 above), but stored under `invite_redeemed`, which reads as an admin-invite metric, not a self-serve paid-activation metric — a future analyst filtering "invite redemptions" to gauge beta-invite health will silently include every Stripe activation too, and vice versa. | Small — either a distinct `kind` for the Stripe-activation-token first-use case, or a `properties` field distinguishing invite-token vs. checkout-token origin at record time (the row would need to carry that distinction, which today it does not). |

## Minimal-additions proposal (SPECIFIED ONLY — not implemented; other agents own these files)

3. Add `events.SUBSCRIPTION_CANCELLED` to `api/funnel.py`'s `FUNNEL_STEPS` list (it's already a valid `events.EVENT_KINDS` member and already recorded — this is a one-line addition to an existing list, no new emit point needed).

## Preservation checklist for the `web/` rewrite

Every one of these must survive the rewrite for instrumentation to keep working. Grouped by file so the other agent can check them off directly.

- **`web/js/api.js`**
  - `trackFunnelEvent(kind, properties)` (currently line 118) — a fire-and-forget `POST /funnel/event` wrapper that `.catch(() => {})`s. Must stay non-blocking and never throw into a caller.
- **`web/js/landing.js`**
  - The `trackFunnelEvent("landing_view")` call in `boot()` (line 43), firing unconditionally on page load of `web/landing.html`.
  - The 5 CTA `data-hook` values currently in `web/landing.html`: `cta-primary`, `cta-signup-hero`, `cta-primary-secondary`, `cta-signup`, `cta-signup-bottom` — these are the natural attachment points for the CTA-click event proposed above; if the rewrite renames or restructures these anchors, the hooks (or equivalent stable selectors) need to survive so click instrumentation has something to bind to.
- **`web/js/signup.js`**
  - The `trackFunnelEvent("signup_started")` call at the end of `renderSignup()` (line 100) — until Gap #1 above is fixed, this is the ONLY client-side signal that a visitor reached the signup view at all; losing it silently drops the funnel back a step with no server-side substitute (the server-side `SIGNUP_STARTED` only fires on actual submission).
  - `data-hook="signup-form"`, `data-hook="signup-email-input"` — needed for the "signup submitted" instrumentation this audit recommends adding at the point of form submit, once that distinct event is designed.
- **Server-side call sites this rewrite must NOT touch or break the contract of** (these live in `api/`/`src/appstate`, owned by the entitlement-editing agent, but the frontend rewrite must keep hitting these same endpoints/response shapes for the events to keep firing):
  - `POST /signup` (`api/signup.py`) — must keep being the thing the signup form's submit handler calls; this is where the real `SIGNUP_STARTED`/`CHECKOUT_STARTED` events live.
  - `GET /signup/complete?session_id=...` (`api/signup.py:216`) — the activation-token bridge; the rewrite's post-checkout redirect page must keep calling this with the Stripe-provided `session_id` query param (see `web/js/signup.js:120-131`'s handling of `session_id` vs. a raw `token`).
  - `POST /betcheck`, `POST /my-bets`, `GET /today`, `GET /games/{date}`, `GET /game/{date}/{away}/{home}`, `GET /changed/{date}` — every one of these carries a bearer token through to `request.state.user_id`, which is what lets their respective `record_event_safe` calls attribute events to a real user. A rewrite that stops sending `Authorization: Bearer <token>` on any of these (e.g. switches to cookies without updating the backend) would silently zero out that route's analytics, not just break auth.

## Concerns

**Blocking:**
- `signup_started` conflates two different real-world moments (viewing the signup form vs. actually submitting it) under one event kind, recorded from two different call sites — this corrupts the one number (`landing_view -> signup_started` conversion) the acceptance criteria most likely cares about. (Gap #1 above.)
- The landing page's headline offer ("Try 3 Bet Checks free... No card required") describes a feature that does not exist in the current backend — the entire bet-check/game surface requires authentication and paid/invite access as of the 2026-09-01 red-team-driven auth change. This is a product-correctness issue surfaced by this audit, not a pure instrumentation gap, but it directly explains why "free Bet Check used" cannot be instrumented: there is nothing to instrument.
- CTA click has zero instrumentation despite 5 distinct CTA placements existing in markup with `data-hook`s seemingly prepared for it.

**Non-blocking:**
- `src/appstate/events.py`'s own module docstring is stale: it claims the `api/today.py` `PAGE_VIEW` call site "stays inert until a future one-line app.py change passes user_id= through" (lines 59-63), but that one-line change already landed at `api/app.py:164`. The code is *better* than the docs claim here, not worse, but the doc drift is exactly the kind of thing that will mislead the next person who reads it without re-verifying against `app.py`, and should be corrected once whoever owns `src/appstate/events.py` next touches it.
- `api/betcheck.py`'s own comment ("No auth dependency guards this route... unauthenticated paid-beta core loop today," lines 40-42) is similarly stale/contradicted by the router-level `_authed_paid` dependency added the same day (`api/app.py:56-91`). Non-blocking for instrumentation itself (the events still fire correctly under auth), but worth a doc fix alongside whatever entitlement work is already touching this file.
- Activation is real (`invite_redeemed` fires correctly for a Stripe-activated token, verified by tracing the token through `issue_invite_token` into the same `tokens` table an admin invite uses), but the event name will read as "an admin invite was redeemed" to anyone querying it later, silently merging two different acquisition channels into one number. (Gap #7.)
- `subscription_cancelled` is recorded correctly and even visible in `GET /admin/overview`'s rollup, but it is excluded from `GET /admin/funnel`'s `FUNNEL_STEPS` list, so there is no single view of the whole acquisition-through-churn arc during the beta.
- "First Gameday/Today view" is emitted with a `route` property that would let it be split out, but no readable surface (`daily_counts_by_kind`, `admin/funnel`) currently does that split — the data exists to answer "did people land on Today or browse Games first" but nothing surfaces the answer today.
- Return-visit/retention has no stored signal or exposed aggregation at all; it is derivable only via a raw `events.list_events()` scan an engineer would have to write by hand.

**[REWRITE RISK] items** — findings above that a `web/` rewrite currently underway could silently break, listed together for convenience: the `landing_view` beacon call, the CTA `data-hook`s (currently unused for tracking but the natural attachment points), the `signup_started` client beacon (the only signal for "reached signup" until Gap #1 is fixed), and the `Authorization: Bearer` header being sent on every authed route (`/today`, `/games/*`, `/betcheck`, `/my-bets`, `/digest`) — losing any of these silently zeroes out that step's data with no error surfaced anywhere, since every emission path is deliberately fire-and-forget / best-effort by design (`record_event_safe`, `trackFunnelEvent`'s `.catch(() => {})`).
