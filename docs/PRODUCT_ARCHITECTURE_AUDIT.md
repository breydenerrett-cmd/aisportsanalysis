## 7. The headline answer, stated first because it is the important one

**THERE IS NO CANONICAL DEPLOYABLE APPLICATION.** Not "it needs work" — it
does not exist.

Verified, not assumed:

| check | result |
|---|---|
| web framework imported anywhere in `src/` or `scripts/` | **none** (no flask, fastapi, django, uvicorn, starlette, aiohttp, tornado, bottle) |
| `http.server` / any server bound to a port | **none** |
| `package.json`, `pyproject.toml`, `setup.py`, `requirements.txt` | **none exist** |
| `Dockerfile`, `Procfile`, `vercel.json`, `netlify.toml` | **none exist** |
| routes, views, URL handling | **none** |
| localhost URL | **none — pages open from `file://`** |

What exists instead is a **static-site generator with no site**: a Python CLI
renders self-contained HTML files to disk. There is no server to host, no
build step, no deploy target, and no runtime a hosting provider could attach
to. Turning this into a SaaS is a real product-architecture project, not a
deployment task.

## 1. The closest thing to a canonical application

| property | value |
|---|---|
| entry point | `python3 -m src.cli brief [--date YYYY-MM-DD]` (`src/cli.py:512 cmd_brief`) |
| renderer | `src/report/dashboard.py` (the slate dashboard), `src/report/ranker.py` (gated, publishes no picks), `src/report/archive.py` (static index) |
| data assembly | `src/pipeline/briefing.py` → `src/detect/dossier.py` → detectors, `src/analysis/*` |
| runtime | Python 3.11, **standard library only** — no numpy, no scipy, no third-party packages |
| output | `artifacts/briefing.html` (one page, all games), `artifacts/analyze_*.html` (one page per matchup), `artifacts/archive.html` (index over both) |
| how it is viewed | opened directly from the filesystem; **no script tags, no external requests, no server** |
| build / deploy | none exists |
| where hosting would attach | nowhere today. The generated HTML *could* be pushed to any static host as-is, which is the cheapest possible first step, but that gives a read-only nightly page — not accounts, not auth, not payments, not per-user state |

The static-only property is deliberate and test-enforced (pages must open from
`file://` with zero script tags), which has been the right call for an
evidence tool. It is also the single biggest gap between what exists and a
subscription product.

## 2 & 3. The dropdown items — what they actually are

**They are published Claude Artifacts, not part of this repository.** They are
individually hosted HTML pages on `claude.ai/code/artifact/...`, published from
earlier sessions on 27–29 August. They are **not** routes, not views, not
builds, and not generated by any code in this repo. Nothing in `src/` produces
or updates them, and deleting them would not change the codebase at all.

That distinction matters: the dropdown is a **gallery of one-off published
pages**, and it is being mistaken for a product with eight screens.

Full per-artifact classification, including which are explainers versus
product-shaped, is in `docs/PRODUCT_ARCHITECTURE_ARTIFACT_AUDIT.md`.

Structural facts that hold regardless of that per-page detail:

- All eight are **historical snapshots**: published once, never regenerated,
  and disconnected from the live pipeline. Any slate data inside them is
  frozen at its publication date.
- None of them reads live data. None can refresh.
- The repo's own `artifacts/*.html` are a **separate** set of generated files
  and are the live product surface.

## 4. Closest representation of what a paying customer would use today

**`artifacts/briefing.html`**, produced by `python3 -m src.cli brief`.

It is the only surface carrying the full current product: the synthesis block
("what matters tonight", 3–5 ranked items with samples attached), matchup
depth, the price-improvement table against de-vigged consensus, the "what
changed" roster-event section with relevance tiers, evidence labels, per-game
permalinks, and the honest "no demonstrated betting edge" headline where
nothing clears the bar.

Second closest: `artifacts/analyze_*.html`, the same depth for one arbitrary
matchup, which is the shape most like a "look up this game" customer action.

Neither has accounts, persistence, interactivity, or a URL.

## 5. Proposed eventual clean split (proposal only — nothing built)

**PUBLIC CUSTOMER PRODUCT**
- Tonight's slate view (from `dashboard.py`)
- Single-matchup analyzer (from the `analyze` path)
- Bet Check / Bet Debunker entry points
- Price-improvement / line-shopping view (never labelled EV)
- "What changed" news and roster timeline
- Archive of past days
- Accounts, billing, auth — **none of which exist in any form**

**INTERNAL RESEARCH / ADMIN**
- Evolution Lab (`src/evolab/`), placebo ceilings, strategy autopsies
- Research families, falsification battery, funnel, matrix
- Slate health monitor (`src/pipeline/health.py`), collection scripts,
  forward ledger, timing report, reproducibility audits
- The Ranker while Engine 2 is `None` — it is currently an honesty artifact,
  not a customer feature

The hard rule that should survive the split: **the customer product and the
research lab must never share an evidence standard.** The Analyzer may show a
labelled observation; the Ranker may not rank on one. That asymmetry is the
reason they are two things.

## 6. Archive plan (nothing deleted)

- `src/report/dashboard.py`, `src/report/archive.py`, `src/pipeline/briefing.py`,
  `src/analysis/*`, `src/detect/*` — the live product path

**MERGE**
- `artifacts/analyze_*.html` — five one-off matchup pages that duplicate what
  the `analyze` command regenerates on demand; the command is the artifact,
  the files are cache

**ARCHIVE (keep, stop treating as product)**
- All eight published Claude Artifacts — historical snapshots, disconnected
  from the pipeline, valuable as a record of how the thinking evolved
- `artifacts/demo_latest.html` — **explicitly protected by standing rule**;
  it is the known-good snapshot that must survive refactors. Never delete.

**DELETE ONLY AFTER VERIFIED REDUNDANT**
- Nothing yet. Every candidate above is either protected, regenerable, or
  historically useful. No deletion is recommended at this time, and none
  should happen without confirming the generating command reproduces the
  artifact byte-for-byte.

## What this implies for the roadmap

The product question is now the largest unbuilt thing in the project, and it
is a different kind of work from everything done so far. Every piece of
customer-visible value — the analysis, the synthesis, the price comparison,
the evidence labels — **already exists and is tested**. What does not exist is
anything that makes it reachable by a person who is not sitting at this
container's filesystem.

That is a well-scoped future task, not a crisis: the hard part (trustworthy
analysis) is built, and the missing part (a web application) is conventional
engineering. It should be planned deliberately rather than grown accidentally
out of the static generator.
