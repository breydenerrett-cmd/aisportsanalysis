## 1. Feature-legitimacy audit

Classification key: **LEGITIMATE_TOTALS_FEATURE** (says something about run
VOLUME, i.e. the sum, not who wins), **MONEYLINE_FEATURE_PRETENDING**
(a signed away-minus-home advantage statement — legitimate for h2h, not for
totals without a rewrite), **NOT_PIT_AVAILABLE** (no point-in-time-safe
historical source for the 2023-24 discovery/replication window).

### 1.1 Existing matrix features (`src/engine/features.py` `FEATURE_SPECS`)

All seven are coded `value = away_X - home_X` (`funnel.py`'s own
convention, built to pick a SIDE). A signed diff between two teams is a
statement about relative advantage, not about the sum of runs — five of
seven have no run-volume reading even after inspection; two (plus one
weaker one) carry per-starter primitives that can be recombined.

| `lineup_platoon_share` | MONEYLINE_FEATURE_PRETENDING | lineup poll + handedness splits | A (2025+ real poll), D unconditionally 2023-24 |

| `primary_pitch_share` (as coded, away/home diff) | MONEYLINE_FEATURE_PRETENDING | pitch-mix concentration | same |

| `starter_groundball_share` (as coded) | MONEYLINE_FEATURE_PRETENDING | Statcast batted-ball | same |

(§1.2, rows 1-3) — everything else is either moneyline-shaped as coded,
not PIT-available for this window, or not yet built. This matches
`docs/RESEARCH_V7_TOTALS.md` §3-§4 exactly; nothing here overrides it.

## 2. Settlement, push, and de-vig conventions

### 2.1 Settlement + push

A totals selection settles **Over** if `total_runs > line`, **Under** if
`total_runs < line`, and is **VOIDED** (excluded from both the win
numerator and the graded denominator, stake conceptually returned) if
`total_runs == line` — this can only occur on an integer-valued line
(§1.1/§2.2/§2.3 of `docs/RESEARCH_V7_TOTALS.md` measured ~25-29% of games
close on an integer line, with a ~2.7-3.1% overall push rate). This is
standard commercial settlement and is the only convention that does not
bias the measured hit rate in either direction (counting a push as a loss
manufactures a false edge against the hypothesis; counting it as a win
manufactures one for it).

### 2.2 De-vig when books quote different lines — two decisions, not one

Unlike h2h (every book quotes the same two sides), totals books quote
different POINT values at the same instant (V7 §1.1: 45-53 distinct line
values pooled per season). "The market's fair view" therefore requires two
separate decisions:

**Decision A — consensus line.** Proposed convention: the **book-count-
weighted mode** of the line at the snapshot (the single point value quoted
by the most books at that instant); ties broken toward the value closer to
the archive's own line-frequency peak (8.5, per V7 §1.1) as a stable
tiebreak rule fixed in advance, never chosen per-event by inspection.
Rejected alternative: a numeric average of quoted lines (e.g. mean of 8.5
and 9.0 → 8.75) — this manufactures a line no book actually offers and
cannot be bet, which defeats the purpose of a "closing line" definition
whose entire job is to describe a real, tradeable price.

**Decision B — consensus price at that line.** Once the consensus line is
fixed, take the de-vigged fair probability **only from books quoting
exactly that line**, using the same proportional two-way de-vig
(`src.core.odds.devig_two_way`, the same primitive `_fair()` already uses
for h2h) averaged across those books — mirroring `_fair()`'s own averaging
discipline (never a single book's number, which moves with list order).
Rejected alternative: pooling de-vigged probabilities across ALL lines
regardless of point value — this mixes the fair probability of "will this
game go over 8.5" with "will it go over 9.5," which are different
propositions; that mixture is not a coherent probability and must not be
used.

Books quoting off the consensus line are excluded from Decision B's
average, not re-weighted or interpolated onto it — interpolating a price
onto a line nobody quoted is exactly the kind of invented number this
family's evidence rules forbid.

## 3. Closing-line definition (the V7 §5.2 problem)

V7's push-rate measurement (§2.3) used a crude proxy — median line at the
archive's LAST recorded snapshot for an event — that the archive's own
module docstring already flags as ~6 hours pre-game median gap, not a true
close, and that proxy produced an unexplained 55/45 Under/Over split that
must not be trusted until resolved.

**Required definition for any totals evaluation build:** the closing line
is the consensus line and consensus price (§2.2, Decisions A+B) taken at
the **latest available snapshot strictly before `commence_time`**, using
whichever snapshot cadence the source actually offers (the archive's
~3x/day polling for 2023-24; the forward `l1_observations` feed's
finer-grained snapshots for anything after that). This is the same
snapshot-selection discipline the F5 evaluation path already uses (frozen
T-2h snapshot, `src/research/f5_eval.py`) — a totals path should use the
LATEST pre-game snapshot rather than F5's fixed T-2h offset only because
totals lines are known to move later and more than F5 h2h prices do
(no data cited here to support that claim beyond it being the reason a
fixed offset was rejected; this is a design choice for the reviewer to
confirm, not a measured result). Whatever definition is adopted here is
binding on both the eventual push-rate re-measurement (replacing V7 §2.3's
proxy) and the evaluation build's own grading — the two are the same
decision, as V7 §5 hard call 2 already noted.

## 4. Evaluation-path decision: standalone vs. widening the funnel

**Recommendation: build a totals-parallel standalone path, mirroring
`src/research/f5_eval.py`'s pattern — do not widen `src/research/funnel.py`.**

Reasons:

- `funnel.py` is a **feature-threshold selection instrument** by
  construction (`validate_spec` requires a `NUMERIC_FEATURES` feature, a
  `back_advantaged` side, and `threshold > 0` — see `MARKETS = ("h2h",)`
  and the `spec["market"] not in MARKETS` guard). Widening `MARKETS` to
  include `"totals"` would still require funnel.py to grow a genuinely
  different settlement path (Over/Under vs. side, push handling, a
  line-aware de-vig) bolted onto machinery whose every other assumption is
  h2h-shaped (two sides, no push, one consensus price at one shared
  quantity). That is not a config change — it is new logic wearing an old
  module's name, which is precisely the trap `f5_eval.py`'s own docstring
  names as the reason it went standalone for F5.
- The totals-specific pieces that are genuinely new — §2's line-then-price
  de-vig, §2.1's push-void handling, §3's closing-line snapshot rule — are
  each small, isolated, and unit-testable in a standalone module the same
  way `f5_eval.py` isolates F5's own new logic (row construction only)
  while reusing everything else.
- What SHOULD be reused, exactly as `f5_eval.py` reuses it: `src.model.
  discovery` for date-clustered effects/p-values/intervals,
  `src.research.battery` at a frozen `RULES_VERSION` for the falsification
  battery, `src.model.family.benjamini_hochberg` for the family-level FDR
  correction. None of that machinery is h2h-specific; it operates on
  `{won, implied, price}`-shaped rows regardless of market.
- A totals path's row shape is `{game_pk, date, season, market="totals",
  consensus_line, side (over/under), implied, price, won}`, with `won`
  computed from the §2.1 settlement rule (`None` when voided, and voided
  rows excluded from `discovery.evaluate`/`battery.run` exactly as a push
  is excluded from a real ledger) — this is a new but small adapter, not a
  rewrite of funnel's internals.

## 5. Validation items required before any family registration

In order, none skippable, mirroring the discipline already run for h2h
families and for `f5_eval.py`'s own guard rails:

1. **Synthetic injection test for the settlement rule.** Construct
   synthetic `(line, total_runs)` triples covering Over, Under, and push
   on both integer and half-point lines; assert the settlement function
   produces exactly the expected `won`/void outcome for each, byte-exact,
   before it ever touches a real row.
2. **PIT negative tests for every candidate feature in §1.2's
   LEGITIMATE_TOTALS_FEATURE rows**, including a dedicated test for the
   MEAN-of-two-PIT-safe-numbers claim (V7 §5 hard call 5) — the claim is
   very likely true by construction but has never been directly tested;
   a short synthetic test (two known-safe per-side values in, one
   known-safe mean out, no leaked future value able to change it) closes
   this before the family runs, not after.
3. **Denominator/hash guards** on the frozen row set, mirroring
   `f5_eval.py`'s exact-count and season-split assertions
   (`F5EvalError` raised, never a silent narrowing) — a totals path needs
   its own frozen manifest (row count, season split, date-window bounds)
   verified before any row is built, and the identity/price-payload hash
   check re-run the same way.
4. **De-vig agreement check.** For a sample of events where multiple books
   quote the SAME consensus line, verify the §2.2 Decision B average is
   stable under a book-order permutation (protects against a list-order
   bug identical to the one `_fair()`'s own docstring warns against for
   h2h) and that no event's fair probabilities sum to something other than
   1.0 within floating-point tolerance.
5. **Battery wiring.** Confirm `src.research.battery.run` accepts the
   totals row shape unmodified (season split, book/date concentration,
   dose-response checks operate on `{won, implied, price}` and a feature
   column — none of that is h2h-specific) with a `dry_run`-style pass that
   builds every row and runs every feature-side check with `won=None`,
   exactly as `f5_eval.py`'s `dry_run=True` mode does, before any real
   evaluation call.
6. **Push-rate re-measurement using the §3 closing-line definition**,
   replacing V7 §2.3's crude proxy, to resolve the unexplained 55/45
   Under/Over split before trusting it as either an artifact or a real
   effect — this is a prerequisite for trusting ANY totals result, not
   just a nice-to-have.

## 6. What must NOT be done

- **Do not reuse the seven existing `FEATURE_SPECS` as coded** (signed
  away-minus-home diffs) for a totals hypothesis merely because they
  already exist and are already wired into `funnel.py` — §1.1 shows five
  of seven have no run-volume reading even after inspection, and the two
  (plus one weak one) that do must go through the §1.2 recombination, not
  be used in diff form.
- **Do not search for a totals edge before this methodology, `docs/
  TOTALS_COVERAGE.md`, and the §5 validation items are complete and
  reviewed.** Pre-registration before inference is not negotiable here
  any more than it was for V1/V2/V4/V5.
- **Do not read any outcome — `total_runs`, over/under result, or any
  price joined to either — anywhere in this methodology pass or its
  supporting coverage script.** `scripts/totals_coverage_audit.py`
  reports row/event/book/line counts only; it does not open
  `mlb_results.csv` or any settlement field.
- **Do not touch the sealed window.** `data/processed/l1_observations.jsonl`
  rows dated 2026-01-01 onward are sealed; `docs/TOTALS_COVERAGE.md`
  reports only aggregate counts across that file, never a date-scoped
  breakdown of it.
- **Do not adopt a "consensus line" via numeric averaging of quoted point
  values** (§2.2) — it manufactures an unbookable line.
- **Do not treat park altitude, weather, or umpire tendency as ready
  features** — §1.2 classifies each (thin-sample, NOT_PIT_AVAILABLE, and
  NOT_PIT_AVAILABLE respectively); none is registrable as coded today.
- **Do not widen `src/research/funnel.py`'s `MARKETS` tuple** to include
  `"totals"` as a shortcut around building the standalone path in §4 —
  the reasons given there are the reasons, not a preference.
- **Do not call `funnel.register_family` or any equivalent registration
  call from this document or its supporting script.** Nothing here is
  registered; §5's items are the gate that must pass first.
