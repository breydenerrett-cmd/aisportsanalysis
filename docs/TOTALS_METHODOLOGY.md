VOLUME, i.e. the sum, not who wins), **MONEYLINE_FEATURE_PRETENDING**
(a signed away-minus-home advantage statement — legitimate for h2h, not for
totals without a rewrite), **NOT_PIT_AVAILABLE** (no point-in-time-safe

## 2. Settlement, push, and de-vig conventions

### 2.1 Settlement + push

A totals selection settles **Over** if `total_runs > line`, **Under** if
`total_runs < line`, and is **VOIDED** (excluded from both the win
numerator and the graded denominator, stake conceptually returned) if
`total_runs == line` — this can only occur on an integer-valued line
(§1.1/§2.2/§2.3 of `docs/RESEARCH_V7_TOTALS.md` measured ~25-29% of games
close on an integer line, with a ~2.7-3.1% overall push rate). This is
standard commercial settlement and is the only convention that does not
bias the measured hit rate in either direction (counting a push as a loss
manufactures a false edge against the hypothesis; counting it as a win
manufactures one for it).

### 2.2 De-vig when books quote different lines — two decisions, not one

Unlike h2h (every book quotes the same two sides), totals books quote
different POINT values at the same instant (V7 §1.1: 45-53 distinct line
values pooled per season). "The market's fair view" therefore requires two
separate decisions:

**Decision A — consensus line.** Proposed convention: the **book-count-
weighted mode** of the line at the snapshot (the single point value quoted
by the most books at that instant); ties broken toward the value closer to
the archive's own line-frequency peak (8.5, per V7 §1.1) as a stable
tiebreak rule fixed in advance, never chosen per-event by inspection.
Rejected alternative: a numeric average of quoted lines (e.g. mean of 8.5
and 9.0 → 8.75) — this manufactures a line no book actually offers and
cannot be bet, which defeats the purpose of a "closing line" definition
whose entire job is to describe a real, tradeable price.

**Decision B — consensus price at that line.** Once the consensus line is
fixed, take the de-vigged fair probability **only from books quoting
exactly that line**, using the same proportional two-way de-vig
(`src.core.odds.devig_two_way`, the same primitive `_fair()` already uses
for h2h) averaged across those books — mirroring `_fair()`'s own averaging
discipline (never a single book's number, which moves with list order).
Rejected alternative: pooling de-vigged probabilities across ALL lines
regardless of point value — this mixes the fair probability of "will this
game go over 8.5" with "will it go over 9.5," which are different
propositions; that mixture is not a coherent probability and must not be
used.

Books quoting off the consensus line are excluded from Decision B's
average, not re-weighted or interpolated onto it — interpolating a price
onto a line nobody quoted is exactly the kind of invented number this
family's evidence rules forbid.

## 3. Closing-line definition (the V7 §5.2 problem)

V7's push-rate measurement (§2.3) used a crude proxy — median line at the
archive's LAST recorded snapshot for an event — that the archive's own
module docstring already flags as ~6 hours pre-game median gap, not a true
close, and that proxy produced an unexplained 55/45 Under/Over split that
must not be trusted until resolved.

**Required definition for any totals evaluation build:** the closing line
is the consensus line and consensus price (§2.2, Decisions A+B) taken at
the **latest available snapshot strictly before `commence_time`**, using
whichever snapshot cadence the source actually offers (the archive's
~3x/day polling for 2023-24; the forward `l1_observations` feed's
finer-grained snapshots for anything after that). This is the same
snapshot-selection discipline the F5 evaluation path already uses (frozen
T-2h snapshot, `src/research/f5_eval.py`) — a totals path should use the
LATEST pre-game snapshot rather than F5's fixed T-2h offset only because
totals lines are known to move later and more than F5 h2h prices do
(no data cited here to support that claim beyond it being the reason a
fixed offset was rejected; this is a design choice for the reviewer to
confirm, not a measured result). Whatever definition is adopted here is
binding on both the eventual push-rate re-measurement (replacing V7 §2.3's
proxy) and the evaluation build's own grading — the two are the same
decision, as V7 §5 hard call 2 already noted.

## 4. Evaluation-path decision: standalone vs. widening the funnel

**Recommendation: build a totals-parallel standalone path, mirroring
`src/research/f5_eval.py`'s pattern — do not widen `src/research/funnel.py`.**

Reasons:

- `funnel.py` is a **feature-threshold selection instrument** by
  construction (`validate_spec` requires a `NUMERIC_FEATURES` feature, a
  `back_advantaged` side, and `threshold > 0` — see `MARKETS = ("h2h",)`
  and the `spec["market"] not in MARKETS` guard). Widening `MARKETS` to
  include `"totals"` would still require funnel.py to grow a genuinely
  different settlement path (Over/Under vs. side, push handling, a
  line-aware de-vig) bolted onto machinery whose every other assumption is
  h2h-shaped (two sides, no push, one consensus price at one shared
  quantity). That is not a config change — it is new logic wearing an old
  module's name, which is precisely the trap `f5_eval.py`'s own docstring
  names as the reason it went standalone for F5.
- The totals-specific pieces that are genuinely new — §2's line-then-price
  de-vig, §2.1's push-void handling, §3's closing-line snapshot rule — are
  each small, isolated, and unit-testable in a standalone module the same
  way `f5_eval.py` isolates F5's own new logic (row construction only)
  while reusing everything else.
- What SHOULD be reused, exactly as `f5_eval.py` reuses it: `src.model.
  discovery` for date-clustered effects/p-values/intervals,
  `src.research.battery` at a frozen `RULES_VERSION` for the falsification
  battery, `src.model.family.benjamini_hochberg` for the family-level FDR
  correction. None of that machinery is h2h-specific; it operates on
  `{won, implied, price}`-shaped rows regardless of market.
- A totals path's row shape is `{game_pk, date, season, market="totals",
  consensus_line, side (over/under), implied, price, won}`, with `won`
  computed from the §2.1 settlement rule (`None` when voided, and voided
  rows excluded from `discovery.evaluate`/`battery.run` exactly as a push
  is excluded from a real ledger) — this is a new but small adapter, not a
  rewrite of funnel's internals.

## 5. Validation items required before any family registration

In order, none skippable, mirroring the discipline already run for h2h
families and for `f5_eval.py`'s own guard rails:

1. **Synthetic injection test for the settlement rule.** Construct
   synthetic `(line, total_runs)` triples covering Over, Under, and push
   on both integer and half-point lines; assert the settlement function
   produces exactly the expected `won`/void outcome for each, byte-exact,
   before it ever touches a real row.
2. **PIT negative tests for every candidate feature in §1.2's
   LEGITIMATE_TOTALS_FEATURE rows**, including a dedicated test for the
   MEAN-of-two-PIT-safe-numbers claim (V7 §5 hard call 5) — the claim is
   very likely true by construction but has never been directly tested;
   a short synthetic test (two known-safe per-side values in, one
   known-safe mean out, no leaked future value able to change it) closes
   this before the family runs, not after.
3. **Denominator/hash guards** on the frozen row set, mirroring
   `f5_eval.py`'s exact-count and season-split assertions
   (`F5EvalError` raised, never a silent narrowing) — a totals path needs
   its own frozen manifest (row count, season split, date-window bounds)
   verified before any row is built, and the identity/price-payload hash
   check re-run the same way.
4. **De-vig agreement check.** For a sample of events where multiple books
   quote the SAME consensus line, verify the §2.2 Decision B average is
   stable under a book-order permutation (protects against a list-order
   bug identical to the one `_fair()`'s own docstring warns against for
   h2h) and that no event's fair probabilities sum to something other than
   1.0 within floating-point tolerance.
5. **Battery wiring.** Confirm `src.research.battery.run` accepts the
   totals row shape unmodified (season split, book/date concentration,
   dose-response checks operate on `{won, implied, price}` and a feature
   column — none of that is h2h-specific) with a `dry_run`-style pass that
   builds every row and runs every feature-side check with `won=None`,
   exactly as `f5_eval.py`'s `dry_run=True` mode does, before any real
   evaluation call.
6. **Push-rate re-measurement using the §3 closing-line definition**,
   replacing V7 §2.3's crude proxy, to resolve the unexplained 55/45
   Under/Over split before trusting it as either an artifact or a real
   effect — this is a prerequisite for trusting ANY totals result, not
   just a nice-to-have.

## 6. What must NOT be done

- **Do not reuse the seven existing `FEATURE_SPECS` as coded** (signed
  away-minus-home diffs) for a totals hypothesis merely because they
  already exist and are already wired into `funnel.py` — §1.1 shows five
  of seven have no run-volume reading even after inspection, and the two
  (plus one weak one) that do must go through the §1.2 recombination, not
  be used in diff form.
- **Do not search for a totals edge before this methodology, `docs/
  TOTALS_COVERAGE.md`, and the §5 validation items are complete and
  reviewed.** Pre-registration before inference is not negotiable here
  any more than it was for V1/V2/V4/V5.
- **Do not read any outcome — `total_runs`, over/under result, or any
  price joined to either — anywhere in this methodology pass or its
  supporting coverage script.** `scripts/totals_coverage_audit.py`
  reports row/event/book/line counts only; it does not open
  `mlb_results.csv` or any settlement field.
- **Do not touch the sealed window.** `data/processed/l1_observations.jsonl`
  rows dated 2026-01-01 onward are sealed; `docs/TOTALS_COVERAGE.md`
  reports only aggregate counts across that file, never a date-scoped
  breakdown of it.
- **Do not adopt a "consensus line" via numeric averaging of quoted point
  values** (§2.2) — it manufactures an unbookable line.
- **Do not treat park altitude, weather, or umpire tendency as ready
  features** — §1.2 classifies each (thin-sample, NOT_PIT_AVAILABLE, and
  NOT_PIT_AVAILABLE respectively); none is registrable as coded today.
- **Do not widen `src/research/funnel.py`'s `MARKETS` tuple** to include
  `"totals"` as a shortcut around building the standalone path in §4 —
  the reasons given there are the reasons, not a preference.
- **Do not call `funnel.register_family` or any equivalent registration
  call from this document or its supporting script.** Nothing here is
  registered; §5's items are the gate that must pass first.

### D1 — Feature classification: sustained, with one correction and one gap

The seven `FEATURE_SPECS` are all `away_X - home_X` (`funnel.py` `_signal`,
lines 299-308), and the five MONEYLINE_FEATURE_PRETENDING calls in §1.1 for
`lineup_platoon_share`, `starter_platoon_gap`, `lineup_vs_primary_pitch`,
`top_minus_bottom`, and `lineup_vs_primary_pitch`-adjacent interactions are
**correct**: each is a relative-advantage statement, and three of them are
explicitly facing-lineup interactions (`funnel.py` lines 97-108), which
cannot be symmetrised into a run-volume quantity at all. No false positives
found in §1.1. No false negatives: nothing classified
MONEYLINE_FEATURE_PRETENDING has a defensible run-volume reading as coded.

**Correction (not an error, an omission that materially strengthens §1.2).**
`funnel.py` states the matrix cross-join convention explicitly: "`away_*`
features describe the away lineup against the HOME starter." So
`away_starter_groundball_share` is the **home** starter's groundball share.
The consequence is favourable and must be stated in §1.2: `mean(away_X,
home_X)` for the three per-starter primitives is the mean over the two
STARTERS and is **invariant to the side-labelling convention** — it is a
genuine game-level run-environment quantity, not a re-badged diff. This is
the strongest available defence of §1.2 rows 1-3 and it is currently absent.

**Gap.** `_signal` returns `None` unless BOTH sides answer; a mean inherits
that rule and must be coded the same way (both sides or `None` — never a
one-sided mean, which silently changes the estimand). §1.2 does not say so.

**AMENDMENT A1.** State the away/home cross-join convention and the
label-invariance of the mean in §1.2; state the both-sides-or-`None`
missingness rule for every combined feature.

**AMENDMENT A2.** Coverage asymmetry (V7 §5.6: groundball 60.1%→84.6%,
velocity 54.6%→75.1% from 2023 to 2024) means the graded population is
**selected on Statcast coverage** and is a different population in each leg.
This is the same hazard F5's post-adversarial amendments mechanised as a
population-shift kill. Add a pre-registered chi-square on graded-population
composition (screen leg vs replication leg), fatal at p < 0.01, decided
before any outcome — mirroring F5's `population_shift_test` /
`POPULATION_SHIFT_FAIL`.

### D2 — De-vig: Decision A introduces real selection bias; Decision B's estimand also changes with the line

Decision A's rejection of numeric averaging is right and stands. But
"consensus price only from books at the modal line" is **not** neutral:
which books sit on the modal line is an attribute of the book, not of the
game. Books that hold an off-consensus line at the close are
disproportionately the ones with independent pricing (and typically the
lowest hold); books at the mode are disproportionately consensus-followers.
The §2.2 rule therefore systematically drops the most informative prices,
and does so at a rate that varies with how contested the number is — i.e.
the selection is correlated with the very quantity a totals hypothesis
would be trying to measure. §1.2's own "line dispersion" row is the
diagnostic that this bias is non-constant across events.

**Alternative (recommended, replaces Decision A as the primary
convention).** Do not pick one consensus line per event at all. Define the
fair probability **per quoted line**: for each distinct line value at the
snapshot, de-vig Over/Under across the books quoting exactly that line, and
admit a (event, line) pair into the population only if it clears a
pre-registered minimum book count (propose n_books >= 3). Grading then
happens at the line actually bet, the "no invented number" rule is
preserved unchanged, and no book is excluded for holding a minority number.
The modal line becomes a reported diagnostic, not a filter. Where a single
consensus line per event is genuinely required (e.g. the push-rate
re-measurement), keep the book-count mode, but publish the book-composition
table at the mode versus off it, and require a fixed-core-book-panel
sensitivity in which the result keeps its sign.

**Decision B is correct in rejecting cross-line pooling** and in mirroring
`_fair()`'s averaging discipline. Two additions are required:

**AMENDMENT A3.** Adopt the per-line convention above (with the >= 3-book
floor pre-registered) as primary; retain modal-line consensus only for
event-level structural measurement, with the book-composition diagnostic
and fixed-panel sensitivity attached.

**AMENDMENT A4.** §2.2 names only proportional de-vig. F5 pre-registers a
three-convention sensitivity (`proportional` / `power` (multiplicative) /
`shin`, all present in `src.core.odds`) and requires the effect to keep its
sign under all three. A totals family must carry the identical requirement;
proportional-only is a weaker gate than the house standard.

**AMENDMENT A5 (estimand, not a style point).** A two-way de-vig of
Over/Under at an **integer** line assigns zero mass to the push, so the
resulting `implied` is a probability *conditional on no push* — a different
estimand from the same number computed at a half-point line, and it is not
comparable across the ~25-29% integer / ~71-75% half-point mixture. Voiding
pushes at settlement (§2.1) is consistent with that conditional reading, so
§2.1 is not wrong — but a family that pools both line types is averaging
two estimands. **Register half-point (non-pushable) lines as the primary
population, and integer lines as a separate pre-registered stratum or
sensitivity.** This also removes most of the push question from the
critical path.

### D3 — Push handling correct; closing-line definition PIT-computable but under-specified

§2.1's void convention is right and the stated reason (either alternative
manufactures a bias) is right. Two leakage-adjacent defects:

**AMENDMENT A6.** The frozen manifest (§5 item 3) must be defined on
**gradeable** rows — line and price present at the closing snapshot —
computed *before* any settlement field is opened. A denominator that is
"rows minus voids" is a post-outcome count and cannot serve as a pre-run
guard. The void count is then a *reported diagnostic*, pre-registered to
fall in V7's measured ~2.7-3.1% band, and a band miss is a falsification
flag, never a re-filter.

**AMENDMENT A7.** "Latest snapshot strictly before `commence_time`" is
computable point-in-time from the archive and is not leakage — but with
~3x/day polling and a median ~6h pre-game gap, the snapshot-to-first-pitch
gap varies per event and is correlated with the polling schedule (late-slate
games get staler lines). Pre-register (a) a **maximum staleness bound**
(propose: latest snapshot within [commence - 12h, commence); events outside
the bound excluded by a rule fixed in advance, and the exclusion count
published), and (b) publication of the staleness distribution by season.
Also (c): `commence_time` must be taken from the snapshot itself, not from
a post-hoc schedule field, or a rescheduled/suspended game silently uses a
revised start time — a genuine PIT hole. A dedicated negative test is
required, in the style of F5's mutation-armed window guard.

The §3 rationale for preferring "latest" over F5's fixed T-2h is
self-declared as uncited. With A7's staleness bound attached, "latest before
commence, within bound" is acceptable; without the bound it is not.

**AMENDMENT A8 (factual reconciliation).** V7 §5 hard call 2 records a
"40/55 over/under split"; §3 above records "55/45 Under/Over". These cannot
both be right. Reconcile before either is cited again — but see D5 first.

### D4 — Standalone path: recommendation upheld; one reuse requirement added

§4's recommendation is correct, and its reasoning is the right reasoning:
`funnel.MARKETS = ("h2h",)` is the smallest part of the problem; push
handling, line-aware de-vig, and Over/Under settlement are new logic that
would wear an old module's name. Reuse of `discovery`, `battery` at a
frozen `RULES_VERSION`, and `benjamini_hochberg` is correct and matches
`f5_eval.py`.

One asymmetry §4 does not address. F5 went standalone because it *selects
nothing*; a totals family **does** need threshold-fired selection — exactly
the machinery `funnel.validate_spec` / `_signal` implements. A standalone
totals module therefore reimplements the one thing the funnel does well,
and the two can silently diverge.

**AMENDMENT A9.** The totals module must either import funnel's
market-agnostic spec-validation and threshold-firing helpers, or carry an
equivalence test asserting identical selection behaviour against funnel on a
shared h2h fixture. Divergent selection semantics between the two research
paths is not acceptable.

### D5 — Hidden outcome-adjacent choice (the most serious finding)

V7 §6 asserts the §2.3 over/under split is a "market-STRUCTURE measurement,"
and §3 above inherits that framing by treating the split as an anomaly to be
"resolved" by re-measurement. **This is not structure. An Over/Under split
requires `total_runs` compared against the line — it is a settlement read,
and it is precisely the full-population, graded-against-its-own-price
statistic that an F5-H1-shaped hypothesis tests.** The direction of that
split is now known to whoever writes the totals hypotheses.

Two consequences, both binding:

**AMENDMENT A10.** Any full-population Over/Under bias hypothesis must be
registered as such — a member of the pre-registered family, entering BH-FDR
over the full family — and must be reported as **already partially read**
(V7 §2.3's proxy measurement disclosed in the registration). It cannot be
presented as a fresh test.

**AMENDMENT A11.** No hypothesis side, threshold, or feature direction may
be chosen in the direction of the observed split. The §3 closing-line
definition must be **frozen before** the re-measurement is run, and the
re-measurement must not be re-run under alternative closing-line definitions
until one removes the anomaly — that is threshold-tuning by outcome. §5
item 6 as written ("resolve the unexplained split") invites exactly this and
must be rewritten to: fix the definition per §3 + A7, measure once, publish
whatever comes out.

### D6 — The six validation items are necessary but not sufficient

8. **Book-composition / selection-bias diagnostic** for the consensus

9. **Closing-line staleness distribution, max-staleness rule, and a

10. **Pre-void frozen denominator** with the void rate as a banded

11. **Population-shift chi-square** on graded-population composition across

## Revision 2 — 2026-09-05 (post-review)

### R1. Feature legitimacy (supersedes §1, incorporates A1, A2)

Same seven `FEATURE_SPECS` classification as §1.1: all `away_X - home_X`
(`funnel.py` `_signal`, lines 299-308), five MONEYLINE_FEATURE_PRETENDING
with no run-volume reading, three (`starter_groundball_share`,
`starter_velocity_gap`, weaker `primary_pitch_share`) carrying per-starter
primitives usable only recombined.

**Cross-join convention (A1).** `funnel.py`: "`away_*` features describe the
away lineup against the HOME starter" — so `away_starter_groundball_share`
is the **home** starter's own value. `mean(away_X, home_X)` is therefore the
mean over the two STARTERS, invariant to the side-labelling convention: a
genuine game-level run-environment quantity, not a re-badged diff. This is
the affirmative case for §1.2 rows 1-3 and must be stated wherever those
features are proposed.

**Missingness rule (A1).** `_signal` returns `None` unless both sides
answer. Every combined feature inherits this exactly: `mean(away_X, home_X)`
is computed only when both per-side values are present; one-sided means are
never substituted. Coded and tested as both-sides-or-`None`, never a
one-sided fallback.

**Population-shift gate (A2).** V7 §5.6 measured Statcast coverage rising
2023→2024: groundball 60.1%→84.6%, velocity 54.6%→75.1%. The graded
population is therefore selected on coverage and differs by leg. Before any
hypothesis using a recombined feature is evaluated, run a pre-registered
chi-square on graded-population composition (screen leg vs. replication
leg: park, home/away split, month, division — the same composition axes F5
checks), **fatal at p < 0.01, decided before any outcome is read**,
mirroring F5's `population_shift_test` / `POPULATION_SHIFT_FAIL`. A fail
kills the affected hypothesis outright; it is not a re-filter.

### R2. Fair probability, de-vig, and consensus (supersedes §2.2, incorporates A3, A4)

**Primary convention: per-quoted-line fair probability.** No single
"consensus line" is chosen for grading. For each distinct line value quoted
at the snapshot, de-vig Over/Under across only the books quoting exactly
that line; admit an (event, line) pair into the population only if it
clears a pre-registered floor of **n_books >= 3**. Grading happens at the
line actually available to be bet. No book is ever excluded for holding a
minority number, and no number is ever invented by interpolation or
averaging across lines (the §2.2 prohibition on numeric-average lines
stands unchanged).

**Modal line: diagnostic only, not a filter.** The book-count-weighted mode
(§2.2 Decision A, tiebreak toward 8.5 fixed in advance) is retained solely
for event-level structural measurement (e.g. the closing-line push-rate
re-measurement, R5) where one number per event is genuinely required. Every
use of the modal-line convention must publish (a) the book-composition
table at the mode versus off it, and (b) a fixed-core-book-panel
sensitivity check in which the result keeps its sign. The modal line is
never used to select or exclude prices for a betting-population
computation.

**Three-convention sign-survival gate (A4).** Any de-vig — per-line or
modal — must be computed under all three of `src.core.odds`'
`proportional`, `power` (multiplicative), and `shin` conventions. A
candidate hypothesis's effect must keep its sign under all three before it
can be called a survivor; proportional-only is not sufficient. This mirrors
the F5 house standard exactly and is not weaker for totals.

### R3. Half-point vs. integer lines (supersedes §2.1/§4's implicit pooling, incorporates A5)

A two-way de-vig at an **integer** line assigns zero mass to the push, so
its `implied` is a probability **conditional on no push (P(over | no
push))** — a different estimand from the same computation at a half-point
line (which cannot push). Pooling both line types averages two estimands
and is not permitted.

**Half-point lines (non-pushable) are the primary population.** Integer
lines are a separate pre-registered stratum or sensitivity, explicitly
named as estimating P(over | no push), never merged into the primary
population's point estimate. This also removes most of the push question
from the critical path: only the integer stratum needs push handling at
all.

Settlement (§2.1: Over if `total_runs > line`, Under if `<`, VOID if `==`,
voided rows excluded from both numerator and denominator) is unchanged and
correct for both strata — it is the pooling of strata into one estimand,
not the settlement rule itself, that A5 corrects.

### R4. Recombined-feature missingness and both-sides-or-None (incorporates A1's coding rule, cross-referenced from R1)

Every combined feature in §1.2/§3.1 (`combined_starter_groundball_share`,
`combined_starter_velocity_gap`, `combined_primary_pitch_share`, and any
future bullpen-workload recombination) is computed **only** when both
per-side primitives are present for that game; absence of either side
yields `None` for the combined feature, never a one-sided value standing in
for the mean. This must be enforced in code (not by convention alone) and
covered by the mean-of-two-PIT-safe-numbers test in validation item 2/9.

### R5. Closing-line definition (supersedes §3, incorporates A6, A7, A11)

**Definition frozen first, measured once.** The closing line/price is the
per-line fair-probability set (R2) or, where a single line is required, the
modal consensus, taken at the **latest available snapshot strictly before
`commence_time`**, subject to:

- **Maximum staleness bound (A7a):** the snapshot must fall within
  `[commence_time - 12h, commence_time)`; events with no snapshot in that
  window are excluded by a rule fixed in advance, and the exclusion count is
  published, never silently dropped.
- **Staleness distribution published (A7b):** the snapshot-to-commence gap
  distribution is reported by season alongside any push-rate or split
  measurement — late-slate games are known to receive staler lines and this
  must be visible, not buried.
- **`commence_time` from the snapshot itself (A7c):** never from a post-hoc
  schedule field, which would silently pick up a rescheduled/suspended
  game's revised start time — a genuine point-in-time hole. A dedicated
  negative test (in the style of F5's mutation-armed window guard) asserts
  a rescheduled-game fixture cannot leak a revised time into the frozen

- **Frozen denominator, pre-void (A6):** the manifest is defined on
  **gradeable** rows — line and price present at the closing snapshot,

  voids" is a post-outcome count and is never used as the pre-run
  denominator. The void count is a reported diagnostic, pre-registered to
  fall in V7's measured ~2.7-3.1% band; a band miss is a falsification

**Freeze-before-measure (A11).** This definition is frozen **before** the

## Lesson — population-shift gate design (2026-09-05)

M1 (totals) died to line-bucket chi2=281.7 and book-count chi2=367.7; M2
(totals) died to feature occupancy; F5-H2 died to tercile occupancy
chi2=12.4 (TOTALS_RESEARCH_RESULTS.md, F5_RESEARCH_RESULTS.md,
TOTALS_POPULATION_AUDIT.md sec6). This section fixes, for the next
pre-registration, how a population-shift test is chosen and what it may do.

**1. Comparability axes vs league-drift axes.** A comparability axis asks
whether the 2024 sample is drawn from the same *kind* of games the 2023
edges/effects were fit on -- book depth, market liquidity, feature
availability/occupancy, schedule composition. A shift here means the two
seasons are not fair test beds for the same fitted object, regardless of
what actually moved in baseball. A league-drift axis -- line level, run
environment, favourite/dog mix -- legitimately moves year to year and is
part of the phenomenon a full-population calibration hypothesis exists to
measure. The line-bucket and book-count chi-squares that killed M1 are
comparability tests (book coverage and market structure changed); a shift
in modal total or favourite/dog split standing alone is a league-drift
finding, not evidence the samples are incomparable.

**2. Which test belongs to which hypothesis type, frozen before results.**
A full-population calibration hypothesis (fits or evaluates over the whole
season's population) is gated by comparability-axis tests only -- book
depth, liquidity, feature/occupancy floors -- because drift in the thing
being calibrated is the object of study, not a threat to validity. A
feature-partition hypothesis (buckets games by a feature, e.g. tercile,
line bucket) is additionally gated by occupancy chi-square on that same
partition, because an uneven partition changes what population each bucket
represents even when the overall season is comparable. The prereg spec
must name, per hypothesis, which axis type each planned test is before any
data is touched -- this determines whether a given chi-square is decorative
or fatal.

**3. Kill vs report-and-stratify.** A comparability-axis failure (fixed
p<0.01, pre-registered threshold) must KILL: the fitted object and the
evaluation population are not the same kind of thing, and no stratification
rescues a comparison that was never apples-to-apples. A league-drift-axis
finding, even a large one, should be pre-registered as report-and-stratify:
publish the shift, split the analysis by the drifted variable if the
prereg said so in advance, and let the calibration question be answered
per-stratum rather than silently killed -- because the drift is the
phenomenon, and killing on it would make full-population calibration
hypotheses untestable by construction. The dividing line is axis type from
item 1, decided before any test runs, never chosen after seeing a p-value.

**4. Required pre-registration checklist item.** Every planned
population-shift test must be run on feature-side counts (bucket
occupancy, book-count occupancy, whatever the hypothesis touches) BEFORE
the spec is frozen, and the outcome (chi-square value, pass/fail against
the fixed threshold) recorded in the spec text itself. M2's kill was by
design -- the spec anticipated it. M1's was not: the fatal chi-square was
discoverable from feature-side counts alone but was only computed at run
time, so a pre-determined kill was discovered rather than pre-declared.
Going forward, "run the shift test pre-freeze and write the number into the
spec" is a gate on registration, not an optional diagnostic -- a spec that
omits this for any planned partition or comparability axis is not eligible
for registration.

**This does not reopen any frozen verdict.** Nothing here revisits or
reweighs TOTALS_FULLGAME_2026H1 or F5_MONEYLINE_CALIBRATION_2026H1; both
verdicts stand exactly as pre-registered and evaluated. This lesson governs
only the design of the next pre-registration's population-shift gates.
